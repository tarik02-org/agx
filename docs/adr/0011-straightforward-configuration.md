# Simplify configuration before freezing the schema

Status: accepted.

## Inline and reusable definitions

Every selection list (scope `add`/`remove`, bundles, harness `add`/`remove`)
accepts references and inline definitions. A string starting with `.`, `/`, or
`~` is a path; any other string is an ID reference. IDs cannot start with those
characters, so the forms never overlap. Mappings are inline definitions with the
same fields as their top-level section, plus `id`. Bundle lists take only bundle
IDs, since an inline bundle would just be its own selection.

```yaml
scopes:
  - directory: ~/work
    add:
      skills:
        - review                          # reference
        - ./skills/local-thing            # path; ID = folder name
        - id: deploy                      # inline content
          description: Deploy this service.
          content: |
            Run `make deploy` and report the release URL.
        - git: https://github.com/team/skills.git   # inline Git source
          rev: 3f2c9e1a8b7d6c5e4f3a2b1c0d9e8f7a6b5c4d3e
          path: skills/review-strict      # ID = folder name
      instructions:
        - ./AGENTS.md                     # ID = file stem
        - id: pnpm
          text: Use pnpm, not npm.
      mcp:
        - github                          # reference
        - id: aperture
          url: https://aperture.tarik02.me/mcp
```

IDs are required for `explain`, `remove`, `agx secret login`, and native MCP
server names. Path skills and Git skills take the folder name, instruction files
their stem; inline content and MCP servers need an explicit `id`. An inline ID
that collides with any other definition is an error, so a reference never
silently changes meaning; repeating a path in another list, even in `remove`,
defines it again. Top-level definitions gain the same `content` and `text` fields.

## Skills written in configuration

A skill with `content` is a whole skill directory described in YAML:

```yaml
skills:
  deploy:
    name: deploy-service          # native skill name; default: last ID segment
    description: Deploy this service and report the release URL.
    frontmatter:                  # extra SKILL.md front matter, passed through
      allowed-tools: [Bash]
    content: |                    # SKILL.md body
      Run `scripts/deploy.sh`, then follow `references/checklist.md`.
    files:                        # other files, relative to the skill root
      scripts/deploy.sh:
        executable: true
        content: |
          #!/bin/sh
          set -eu
          make deploy
      references/checklist.md: ./docs/release-checklist.md   # copied file
      assets/: ./deploy-assets/   # copied directory (trailing slash)
```

The ID addresses the skill in configuration (`team/deploy` in a package); `name`
is what harnesses show and invoke, defaulting to the ID's last segment, and must
satisfy native naming rules (lowercase letters, digits, and hyphens). Generated
`SKILL.md` front matter holds `name`, `description`, and `frontmatter`, which
cannot redefine those two. `files` keys are relative paths that stay inside the
skill root and cannot name `SKILL.md`; a value is inline text, a `{content,
executable}` mapping, or a path whose file or directory (trailing slash on both
sides) is copied, resolved like other resource paths. Generated skills are
artifacts: their files are hashed into the snapshot like path skills.
Path and Git skills take `name` and `description` from their own `SKILL.md`;
setting them, `frontmatter`, or `files` on such a skill is an error.

An inline `git` source is an anonymous package: it is locked like one unless it
is pinned (below), under the resource's kind and ID (`skill:review-strict`), and
its path must stay inside the checkout.

## Pinned sources skip the lock

A source is pinned when it carries a full 40-character commit `rev`, a `hash`
(the content hash agx records in locks, verified at install), or a path inside
`/nix/store`, which Nix keeps read-only. Pinned sources write no lock entry, so a
fragment whose packages are all pinned, such as one generated by Nix, needs no
lockfile. Unpinned sources keep today's per-fragment lockfiles: each fragment's
packages lock beside it or at its `lockfile`, so fragments from different
repositories carry their own locks.

## Instruction order

Selected instructions concatenate in resolution order: shallower scopes before
deeper ones, harness rules last, and list order within a rule, so more specific
guidance comes later. An optional integer `order` (default `0`) sorts before
that, lower first, for text that must lead or close regardless of where it was
selected.

## Smaller changes

- `remove` replaces `exclude` in scopes and harnesses.
- `version` is dropped; there is no format versioning yet.
- A harness's `args` may be a flat string list, meaning one group for every
  session mode; the list-of-groups form remains for mode-scoped groups.
- Paths accept a leading `~` or `~/`, expanded to the home directory of the user
  running agx: scope directories, imports, lockfiles, package and resource paths,
  `!file`, and executables, including an MCP server's command and `cwd`. `~user`
  and `${VAR}` are not supported, and package manifests cannot use `~`.

Rejected: string shorthands for imports (`local.yaml?`, implicit globs), which
add rules for a rarely written section; ID derivation for inline MCP servers,
whose ID is user-facing in logins and tool names.
